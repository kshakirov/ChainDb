## Description

# [ARCH] Command Parsing Core and Closure-Based Internal Representation

## Контекст

В ChainDb уже работает первый вертикальный проход через runtime:

```text
FIFO
  ↓
poll-fifo-source
  ↓
bytevector
  ↓
decoder / validator
  ↓
procedure
  ↓
ready queue
  ↓
dispatcher
```

На предыдущем этапе `validate-cmd` возвращал процедуру, но dispatcher всё ещё знал детали её вызова:

```scheme
(task 1)
```

Это нарушает границу между механизмом диспетчеризации и семантикой конкретной команды.

Следующий этап — определить единое ядро разбора команд и окончательно зафиксировать внутреннее представление задачи.

---

## Основное архитектурное решение

Внутри ChainDb команда существует только в одном исполняемом представлении:

```text
Task := () → Result
```

То есть после успешного разбора внешнего сообщения результатом всегда является нуль-аргументная Scheme procedure.

Аргументы команды замыкаются внутри процедуры в момент её создания.

Пример:

```scheme
(define (create-get-key-procedure key)
  (lambda ()
    (get-key key)))
```

После:

```scheme
(create-get-key-procedure 1)
```

мы получаем готовую задачу:

```text
#<procedure>
```

Dispatcher не знает:

- имя команды;
- количество аргументов;
- типы аргументов;
- каким протоколом команда была передана;
- каким parser/decoder она была получена.

Он знает только:

```scheme
(task)
```

---

## Почему не вводим второе внутреннее представление

Не вводим отдельную обязательную промежуточную форму вроде:

```scheme
'(get-key 1)
```

с последующим `eval`, `compile` или дополнительной интерпретацией в dispatcher.

Такая форма может временно существовать внутри конкретного parser-а как локальная техническая структура, но она не является контрактом между модулями.

Граница parser/runtime выглядит так:

```text
external representation
        ↓
      decoder
        ↓
 executable closure
```

Таким образом, у системы существует одно каноническое внутреннее представление команды — процедура.

---

## Внешние кодировки

Wire-format не является частью семантики команды.

Первый наивный формат может выглядеть так:

```text
get::1::#get::2::#
```

где:

```text
#    — граница команды
::   — граница поля
get  — внешний opcode / имя операции
1    — параметр
```

Decoder этого формата выполняет:

```text
get::1::#
   ↓
recognize GET
   ↓
extract key = 1
   ↓
create-get-key-procedure
   ↓
#<procedure>
```

Позже могут появиться другие носители и кодировки:

```text
text protocol
binary protocol
HTTP
socket frames
FIFO
```

Каждый из них имеет свой внешний decoder, но после декодирования все они приходят к одному результату:

```text
Task := procedure
```

---

## Общее ядро команд

Семантика команды не должна дублироваться между кодировщиками.

Например, все внешние представления GET должны в итоге обращаться к одному конструктору:

```scheme
(create-get-key-procedure key)
```

Концептуально:

```text
text GET ───┐
            │
binary GET ─┼──→ create-get-key-procedure ─→ Task
            │
HTTP GET ───┘
```

Таким образом:

- decoder отвечает за внешний формат;
- command core отвечает за смысл операции;
- command factory создаёт closure;
- dispatcher работает только с готовой procedure.

---

## Целевая архитектура

```text
             Transport / Encoding
                     ↓
              Transport Decoder
                     ↓
              Command Parsing Core
                     ↓
             Command Factory
                     ↓
              Closure / Task
                     ↓
                Ready Queue
                     ↓
                Dispatcher
                     ↓
                   task()
```

Для конкретной команды:

```text
get::1::#
    ↓
parse
    ↓
GET + key=1
    ↓
create-get-key-procedure(1)
    ↓
(lambda () (get-key 1))
    ↓
ready queue
    ↓
dispatcher
    ↓
(task)
```

---

## Разделение ответственности

### Decoder

Знает:

- формат входных байтов;
- границы сообщений;
- кодирование полей;
- внешний opcode.

Не знает:

- scheduler;
- ready queue;
- continuation machinery;
- dispatcher implementation.

### Command Core / Factory

Знает:

- какие команды существуют;
- какие аргументы обязательны;
- как проверить параметры;
- какую closure создать.

Пример контракта:

```text
GET : key → Task
PUT : key × value → Task
DEL : key → Task
```

### Dispatcher

Знает только:

```text
Task := () → Result
```

Dispatcher не разбирает и не интерпретирует команды.

---

## Первый минимальный эксперимент

Реализовать только GET.

Внешнее сообщение:

```text
get::1::#
```

Парсер должен:

1. выделить одну команду;
2. распознать `get`;
3. получить аргумент `1`;
4. проверить обязательный параметр;
5. вызвать фабрику GET;
6. вернуть готовую procedure.

Пример:

```scheme
(define (create-get-key-procedure key)
  (lambda ()
    (get-key key)))
```

Dispatcher должен получить её и выполнить только:

```scheme
(task)
```

Без:

```scheme
(task 1)
```

и без знания о GET.

---

## Следующие шаги

1. Убрать `(task 1)` из dispatcher.
2. Сделать GET command factory, возвращающий нуль-аргументную closure.
3. Сделать минимальный parser для текущего формата `get::key::#`.
4. Отделить parsing внешнего формата от создания команды.
5. Добавить вторую команду и проверить, что dispatcher не меняется.
6. Позже добавить альтернативный decoder для другой кодировки и убедиться, что command core также не меняется.

---

## Критерий завершения

Тикет считается завершённым, когда:

```text
wire bytes
   ↓
decoder
   ↓
command core
   ↓
closure
   ↓
ready queue
   ↓
dispatcher
   ↓
task()
```

работает для минимум двух команд, при этом:

- dispatcher не знает сигнатур команд;
- command core не знает transport;
- разные кодировки используют одну и ту же семантику команд;
- единственным runtime-представлением команды является Scheme procedure;
- аргументы команды полностью замкнуты внутри task до постановки в ready queue.

Сегодня отделили упражнение от механизма и появился самостоятельный модуль `(chainDb parser)`.

Что уже есть:
- parser принимает одну целую строку команды вида `!get::1#`;
- `decode-op` и `decode-arg` съедают свой фрагмент и возвращают значение вместе с остатком входа;
- `decode-cmd` связывает эти шаги и для текущего примера возвращает `("get" . "1")`;
- старый `test_validate_command.ss` очищен от копий parser/closure-кода и теперь импортирует публичный модуль;
- граница dispatcher выровнена: `run-cmd` возвращает готовый нуль-аргументный task, dispatcher делает `(spawn task)` и не знает сигнатуру команды;
- пустой bytevector больше не порождает бесконечную fake-задачу.

Чистый Chez импортировал новый модуль и подтвердил разбор `!get::1#` в `("get" . "1")`.

На следующий раз берём намеренно узкий вертикальный шаг: считаем, что одна полная команда приходит одним куском, разбираем GET, создаём и выполняем closure через dispatcher, затем подключаем настоящее hash-хранилище — то есть впервые запускаем уже саму базу. Потоковое склеивание неполных строк и несколько команд в одном chunk пока сознательно не тащим в этот шаг.
