## Description

## Зачем

Текущий рабочий контур уже доказан: входной bytevector проходит через parser, `run-cmd` создаёт задачу, `PUT` пишет в storage, `GET` читает и может уступать управление через continuation. Но внутри этого пути мы слишком рано переходим к строкам:

`bytevector → string → char list → string opcode / char-list arguments → string key/value`

Пока мы не ушли далеко, переводим ядро протокола и storage на байтовое представление.

## Архитектурное решение

Parser в ChainDb — не универсальный синтаксический парсер. Это декодер нашего протокола, поэтому он знает допустимые команды и сразу переводит внешний байтовый формат во внутреннее представление.

На первом шаге внутренний opcode проще представить символом (`get`, `put`) и исполнять через `case`. Это даёт прямую диспетчеризацию без повторных `string=?`. Числовой opcode можно ввести позже, если он понадобится формату протокола или будет оправдан измерениями; тащить его заранее только ради предполагаемой экономии не нужно.

Аргументы команды, ключи и значения остаются bytevector. Строки используются только на границе диагностики/вывода человеку.

Ожидаемая форма после декодирования концептуально:

```scheme
(get #vu8(...key...))
(put #vu8(...key...) #vu8(...value...))
```

Исполнитель выбирает ветку через `case` и возвращает диспетчеру thunk, как и сейчас.

Storage для ключей использует содержательное сравнение bytevector:

```scheme
(make-hashtable equal-hash bytevector=?)
```

Отдельно договоримся, что ключ после помещения в storage не изменяется.

## Что сделать

- Переписать parser так, чтобы он принимал bytevector и не прогонял команду через `utf8->string` / `string->list`.
- Распознавать известный opcode непосредственно при декодировании и возвращать внутренний тег команды.
- Возвращать аргументы как bytevector.
- Перевести `run-cmd` на `case` по opcode.
- Перевести ключи и значения storage на bytevector.
- Оставить текущую модель исполнения: каждая распознанная команда создаёт thunk для dispatcher; `GET` может использовать yield, короткий `PUT` выполняется за один такт.
- Удалить строковые преобразования из внутреннего пути, оставив их только для отладочного отображения.

## Минимальные проверки

- Два разных bytevector с одинаковыми байтами обозначают один ключ в storage.
- `PUT` через `run-cmd` сохраняет байтовое значение.
- Следующий `GET` по отдельно созданному, но равному bytevector возвращает это значение.
- Parser различает `GET` и `PUT` и отдаёт внутренние opcode.
- Исполнитель отвергает неизвестный opcode и неверное число аргументов без попытки обратиться к `car`/`cadr` пустого списка.
