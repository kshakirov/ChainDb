## Description

## Откуда пришли

После завершения неблокирующего FIFO-чтения появился первый вертикальный проход через runtime:

```text
FIFO → poll → bytevector → validate-cmd → procedure → spawn → ready queue → dispatcher
```

`poll-fifo-source` уже возвращает данные внешнего события. `validate-cmd` отличает отсутствие команды от команды и возвращает исполняемую процедуру. Dispatcher не разбирает содержимое bytevector сам: он получает вычисление, ставит его в очередь и исполняет обычным механизмом задач.

Это первый работающий набросок той архитектуры, к которой теперь переделываем ChainDb целиком.

## Куда идём

- `main` только собирает настройки/источники и запускает runtime;
- dispatcher становится композиционным центром: опрашивает внешние источники, принимает готовые события/задачи и управляет ready queue;
- источники ввода не знают о commands, storage и scheduler;
- разбор команды превращает входные данные в закрытую исполняемую задачу;
- dispatcher не знает сигнатур конкретных команд и запускает нуль-аргументные task-thunk;
- модули соединяются направленно, без циклических и случайных горизонтальных зависимостей;
- внешних источников может быть несколько, а механизм их опроса остаётся единым.

Целевая граница:

```text
EventSource : () → NoEvent | Event
Decode      : Event → Invalid | Task
Task        : () → Result
```

## Следующие шаги

1. Переименовать `make-dispatcher-sleep`: это уже не сон, а ожидание/опрос внешних источников.
2. Убрать знание `(task 1)` из dispatcher: `validate-cmd` должен вернуть полностью подготовленный thunk.
3. Выделить регистрацию/коллекцию event sources и определить результат их неблокирующего опроса.
4. Развести жизненный цикл FIFO-дескриптора и отдельные акты polling/read, не открывая новый fd бесконечно.
5. Пропустить настоящую команду через decoder → task → storage и закрепить вертикальным тестом.
6. По этому образцу постепенно выровнять зависимости остальных частей базы.

## Критерий завершения

`main` конфигурирует и запускает runtime; dispatcher одинаково работает с одним или несколькими источниками и планирует непрозрачные для него task-thunk; конкретные команды и storage не протекают в механизм event loop/очереди; вертикальный тест показывает путь внешнего события до результата команды.
