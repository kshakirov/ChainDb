## Description

## Идея

Первая графовая модель ChainDb строится поверх уже работающего byte-native in-memory ядра. Мы не создаём объектный слой, JOIN-механику или отдельный язык хранения: вершины и рёбра остаются бинарными данными, а навигация обеспечивается дополнительными hash-индексами.

## Базовое представление

### Вершины

- Идентификатор: `bytevector`.
- Значение: бинарный blob свойств вершины.
- Точечный доступ по ID: ожидаемо `O(1)` через `equal-hash` + `bytevector=?`.

Концептуальный внешний ключ:

```text
node:<id>
```

### Рёбра

Ребро задаётся тройкой:

```text
<src-id, label, dst-id>
```

Все три компонента являются bytevector. Метаданные ребра — bytevector или пустой `#vu8()`.

Концептуальный полный ключ:

```text
out:<src-id>:<label>:<dst-id>
```

Полностью заданное ребро проверяется через hash за ожидаемое `O(1)`.

## Adjacency-индексы

Обычный hashtable не поддерживает prefix/range scan. Поэтому выражение `out:<src>:*` нельзя реализовывать перебором всей основной таблицы: это было бы `O(N)`.

Добавляем два внутренних индекса:

```text
out-index: src-id → коллекция исходящих edge descriptors
in-index:  dst-id → коллекция входящих edge descriptors
```

Edge descriptor на первом шаге содержит достаточно байтов, чтобы получить `label`, соседний ID и полный edge-key без строковых преобразований.

Сложности:

- точечный node lookup: ожидаемо `O(1)`;
- точечный edge lookup: ожидаемо `O(1)`;
- вход в adjacency collection: ожидаемо `O(1)`;
- перечисление соседей: `O(degree)`;
- фильтрация по label в первой версии может быть `O(degree)`; отдельный `(node,label)` индекс добавляется только при доказанной необходимости.

## Binary-first правила

- В runtime не используются JSON, строки и `string-append` для ключей.
- Parser и graph layer работают с bytevector/u8.
- Символы допустимы только как внутренние opcode, а не как пользовательские ID или label.
- Формат составного ключа не должен зависеть от разделителя `:`, если ID и label допускают произвольные байты.
- Для надёжного бинарного кодирования используем type tag и length-prefixed поля, например:

```text
[type][src-length][src][label-length][label][dst-length][dst]
```

Читаемые формы `node:<id>` и `out:<src>:<label>:<dst>` являются описанием структуры, а не обязательным физическим кодированием.

## Инварианты

При добавлении ребра согласованно обновляются:

1. основная запись ребра;
2. `out-index` источника;
3. `in-index` назначения.

Удаление ребра обязано убрать запись из всех трёх мест. До появления транзакций эти изменения выполняются одной короткой командой без `yield`, чтобы dispatcher не наблюдал частично обновлённый граф.

## Первый минимальный API

```text
ADD-NODE <id> <blob>
GET-NODE <id>
ADD-EDGE <src> <label> <dst> <metadata>
GET-EDGE <src> <label> <dst>
OUT-NEIGHBORS <src>
IN-NEIGHBORS <dst>
```

Имена окончательно утвердим при реализации; важно сначала закрепить семантику.

## План реализации

1. Определить бинарные constructors/selectors для node-key и edge-key.
2. Добавить graph storage поверх существующего bytevector storage.
3. Реализовать `out-index` и `in-index`.
4. Добавить node/edge commands в byte-native parser и `case` dispatcher.
5. Закрепить тестами точечный доступ и обход в обе стороны.
6. Добавить длинный BFS/DFS как первую graph-задачу, которая периодически делает `yield`.

## Критерии первого этапа

- Два разных bytevector с одинаковым содержимым обозначают одну вершину.
- Добавленное ребро находится по полной тройке.
- Исходящий обход возвращает `dst`.
- Входящий обход возвращает `src`.
- Ребро с пустыми metadata работает.
- Добавление ребра не оставляет рассогласованные out/in индексы.
- Графовый слой не переводит пользовательские данные в строки.

Продолжает alpha-ядро `0.1.0-alpha.1` и byte-native работу из issue #6.
